Изменения относительно исходного коммита `fcec8cf5`.

### Новые возможности

**Передача картинок через буфер обмена.**
Раньше через буфер обмена ходил только текст: скопировать снимок экрана или фрагмент изображения было нельзя никак. Теперь картинки передаются в обе стороны в формате PNG — он выбран как формат без потерь, потому что в буфер обмена чаще попадают снимки экрана и схемы, чем фотографии, а их сжатие с потерями портит заметнее всего.
Прозрачность при вставке теряется: у точечных рисунков Windows нет надёжного способа её передать, и приложения по-разному трактуют четвёртый байт. Для снимков экрана и фотографий это не имеет значения.
Если в буфере есть и текст, и картинка — передаётся текст. Приложения обычно кладут рядом с картинкой её текстовое представление, и чаще именно текст и хотели скопировать; типичный пример — диапазон, скопированный из Excel. В журнал при этом записывается, что картинка была отброшена, так что решение можно будет пересмотреть по накопленным данным.
Ограничение в 4 МБ действует и здесь: подробный снимок экрана 4K способен его превысить, и тогда картинка не передастся, о чём будет запись в журнале.

### Исправления

**Захват экрана зависал после разблокировки компьютера.**
При подключении к заблокированному компьютеру после ввода пароля картинка замирала: приходил один и тот же частично отрисованный кадр, при этом соединение считалось исправным и не разрывалось. Переподключение не помогало.
Причина: интерфейс дублирования рабочего стола (DXGI Desktop Duplication) привязан к рабочему столу, на котором был создан. После перехода с экрана блокировки на рабочий стол пользователя он переставал отдавать кадры, но не сообщал об ошибке `DXGI_ERROR_ACCESS_LOST` — вместо этого бесконечно возвращал `DXGI_ERROR_WAIT_TIMEOUT`, что трактовалось как «на экране ничего не изменилось». Дублирование при этом никогда не пересоздавалось, а клиенту повторно отправлялся устаревший кадр, сохранённый на момент переключения.
Исправление: при смене рабочего стола объекты дублирования освобождаются, и захват заново привязывается к текущему рабочему столу — так же, как это уже делал GDI-захватчик.
*Статус: исправление собрано, но на проблемном компьютере ещё не проверено.*

**Задержки в работе и «слайд-шоу» при активности на экране.**
Работать было тяжело: изображение обновлялось рывками, ввод отставал, при подключении двух консолей становилось заметно хуже.
Причина: масштабирование и кодирование видео выполнялись синхронно в главном потоке, вместе с сетевым вводом-выводом, межпроцессным обменом и передачей ввода. Один поток оказывался загружен полностью, а остальные ядра простаивали; при нескольких клиентах кодирование для них шло последовательно.
Исправление: кодирование вынесено в отдельный поток для каждого клиента. Кадр копируется из разделяемой памяти до передачи в поток, поэтому буфер захвата можно переиспользовать сразу. Если кодировщик ещё занят, кадр пропускается, а не ставится в очередь — для видео в реальном времени свежий кадр важнее полного.
*Статус: подтверждено измерением — нагрузка распределилась по потокам, ни одно ядро не загружено полностью, потребление памяти стабильно.*

**Агент рабочего стола зацикливался после отключения клиента.**
После завершения сеанса агент мог уйти в бесконечный цикл: цикл событий оказывался занят целиком, процесс переставал отвечать — в том числе на собственное завершение, — а в журнал писалось около десяти тысяч одинаковых записей в секунду. На рабочей машине это дало 28 ГБ журналов за сутки.
Причина: запрос на следующий кадр мог прийти уже после отключения сеанса — он был отправлен до того, как команда на отключение успела обработаться. Обработчик перезапускал таймер захвата с нулевой задержкой, не проверяя, включён ли сеанс. Захватчик экрана к этому моменту был уже освобождён, поэтому обработчик кадра сразу выходил с ошибкой, не взводя таймер заново. Таймер же повторяющийся — и продолжал срабатывать на каждой итерации цикла событий.
Исправление: запросы на захват для отключённого сеанса игнорируются, а таймер не остаётся взведённым с нулевой задержкой, когда захватчика нет. Ошибка найдена по журналам с рабочей машины; в upstream она исправлена схожим образом.
*Статус: исправление собрано, наблюдение за журналами на рабочих машинах продолжается.*

**Некорректные зашифрованные пакеты могли завершить процесс аварийно.**
Сообщение короче тега аутентификации приводило к вычислению отрицательной длины и чтению за границей буфера. Проверка добавлена в расшифровщик (перенесено из upstream) и дополнительно у вызывающей стороны: в нашей ветке размеры беззнаковые, поэтому вычитание заворачивалось в огромное значение, и выделение буфера происходило до проверки.

**Передача файлов на заблокированный компьютер сообщала о неверной причине.**
При попытке передать файлы на компьютер с заблокированным экраном операция отклонялась с сообщением «Нет пользователя, вошедшего в систему» — хотя пользователь в системе был, просто экран заблокирован. Причина отказа выглядела необъяснимой, и такое поведение обычно принимали за должное.
Исправление: для заблокированной сессии добавлен отдельный код ошибки, и сообщение теперь подсказывает, что делать — разблокировать компьютер. Сам запрет на передачу при блокировке сохранён намеренно: это защита от выгрузки файлов с оставленного без присмотра рабочего места. Теперь по сообщению видно, требуется разблокировать компьютер или войти в систему.
*Статус: проверено на рабочих машинах — для заблокированного компьютера и для компьютера без вошедшего пользователя выдаются разные сообщения.*

**Передача файлов могла прекратиться без сообщений.**
Если от хоста приходил ответ, который не удавалось разобрать, обработчик завершался, не сняв запрос с очереди и ничего не сообщив. Ответы сопоставляются с запросами по порядку очереди, а следующий запрос отправляется только при получении ответа, — поэтому очередь больше нечем было разгрести, и все последующие операции молча в ней накапливались.
Исправление: запрос снимается с очереди, а вместо тишины показывается сообщение об ошибке.

**Копирование очень большого текста разрывало соединение.**
Сообщение, не помещающееся в предел канала (7 МБ), считается нарушением протокола, и соединение закрывается. Скопировать столько текста удаётся нечасто — это миллионы символов, например содержимое большого журнала, — но сеанс при этом терялся целиком, вместе с передачей файлов и всем остальным.
Исправление: содержимое буфера обмена больше 4 МБ не отправляется. В журнал пишется предупреждение, соединение продолжает работать, не синхронизируется только сам буфер. Предел взят с запасом ниже семи мегабайт: поверх данных ложатся обёртка protobuf, шифрование и объемлющее сообщение.
Та же проверка стоит и на приёме. Пока передаётся только текст, но когда дойдёт до картинок, этот предел станет обязательным: снимок экрана перешагнёт его без труда.

**Звук с удалённого компьютера перестал передаваться.**
В версии 2.7.0 звук работал, в 3.0.0 захват перестал запускаться вовсе: каждая попытка завершалась ошибкой «не был произведён вызов CoInitialize», и так при каждом подключении.
Причина — очерёдность. COM инициализируется в потоке, но делается это внутри `run()`, а Qt испускает сигнал `started` **до** входа в `run()`. Захватчик звука создаётся по этому сигналу, то есть обращается к COM раньше, чем тот готов. В 2.7.0 та же инициализация выполнялась в собственном классе потоков и успевала раньше; при переходе на потоки Qt порядок изменился, и это осталось незамеченным.
Исправление: добавлены сигналы `sig_beforeRunning` и `sig_afterRunning`, испускаемые изнутри `run()` — когда COM уже готов и ещё не освобождён. Все пять мест, работавших через `started` и `finished`, переведены на них.
Попутно устранены ещё две неисправности. Потоки с диспетчером Asio теперь входят в многопоточную модель COM вместо однопоточной: последняя создаёт скрытое окно сообщений, а работа со звуком рассчитана на первую. И завершение работы потока больше не освобождает объекты COM после того, как COM для этого потока уже выгружен.

### Обновление и диагностика

**Установка новой сборки поверх предыдущей.**
Пакеты MSI не обновлялись поверх уже установленных — требовалось сначала удалить программу. Причина: сборки выпускались с одинаковой версией, а обновление равной версии было запрещено (`AllowSameVersionUpgrades="no"`), при этом код продукта генерировался заново, и установщик считал пакет другим продуктом. Теперь обновление равной версии разрешено во всех пакетах.

**Определение сборки по журналу.**
Раньше по журналу нельзя было понять, какая именно сборка работает: номер версии включает число коммитов, поэтому разные сборки одного коммита неразличимы. Теперь при запуске записываются:
- время компоновки модуля (берётся из заголовка исполняемого файла, уникально для каждой сборки);
- отметка, если сборка сделана из изменённых, но не зафиксированных исходников;
- перечень загруженных модулей Aspia с версией и временем компоновки каждого.
Если версии модулей не совпадают (например, исполняемый файл от одной сборки, библиотека от другой — обычное следствие неудачного обновления), в журнал записывается предупреждение. Работа при этом не прерывается: версии могут оставаться совместимыми.

**Учёт непередаваемых форматов буфера обмена.**
Передаётся только текст, всё остальное молча теряется. Теперь в журнал записывается, что именно не удалось передать, — отдельно два случая: когда пригодного содержимого не было вовсе и когда текст взят, но рядом лежала картинка или список файлов. Второй случай важнее: там содержимое не теряется, а незаметно ухудшается до текста, и именно так это выглядит при копировании из Excel или браузера.
Записываются **только названия форматов — никогда содержимое**. В буфер обмена регулярно попадают пароли, а журналы собирают и передают для разбора.
Смысл в том, чтобы выбирать форматы для поддержки по тому, что действительно встречается на рабочих машинах, а не по догадкам.

**Журналы могли занять весь диск.**
Старые файлы удалялись только по возрасту — старше двух недель. Предела на общий объём каталога не было, поэтому при сбое, когда запись идёт непрерывно, ничего не спасало: на одной рабочей машине за сутки накопилось 28 ГБ, все файлы были свежие, под удаление не подпадал ни один, и уборка исправно удаляла ноль.
Исправление: добавлен предел общего объёма каталога — 256 МБ по умолчанию, задаётся переменной среды `ASPIA_MAX_LOG_DIR_SIZE`. При превышении удаляются самые старые файлы, пока объём не уложится. Порядок удаления задан явно, а не через сортировку Qt: ошибка в направлении стёрла бы самые свежие журналы, то есть именно те, ради которых предел и вводился.
Попутно исправлено: перечисление каталога отбирало ещё и подкаталоги со ссылками `.` и `..`, которые затем безуспешно пытались удалить; а если файловая система не хранит время создания файла, прежняя проверка возраста могла удалить сразу всё.

**Стартовые сведения записываются всегда**, независимо от настроенного уровня подробности. Иначе на компьютерах, где ведётся запись только ошибок, журнал оказывался пустым — именно там, откуда его обычно и запрашивают. Записывается один раз за запуск, на размер журнала не влияет.

- Номер версии берётся из `CMakeLists.txt` — одним источником и для исполняемых файлов, и для пакетов MSI.
- Путь к WDK можно задать явно через `WDK_TARGET_VERSION`, вместо поиска произвольной установленной версии.

Remote desktop, file transfer and system information tool.

With Aspia, you can create your own NAT traversal infrastructure (using Router and Relay servers) with connection by ID or use direct connections. Aspia supports many features. Among them, detailed information about the system, audio, text chat.

Currently supported
-------------------
- Remote desktop management
- Remote desktop view
- File transfer
- System information
- Text chat
- Task manager
- Encryption
- Authorization (it is possible to add users with different access rights)
- Address book with encryption and master-password
- <b>NAT traversal with connection by ID</b> (with using Aspia Router and Aspia Relay)
- Direct connections
- Audio support
- Video recording
- Client and Console for Windows, MacOSX and Linux
- Host for Windows only
- Router/Relay for Windows and Linux
- And much more

System requirements
-------------------
- Windows 7/2008 R2 or higher (x86 or x86_64 CPU)
- Debian 11/Ubuntu 20.04 Linux (x86_64 CPU)
- MacOSX (x86_64 or ARM64 CPU)
